## Частина A. Що робимо

### Узгоджені значення

Замовник залишив вибір за виконавцем; обрано таке, кожне значення живе в одному місці конфігурації.

- **Стек:** поточний погоджений baseline R1: Node.js 22, TypeScript 6.x (`strict`), Next.js (App Router) + React, Leaflet 1.9.x (бібліотека карт), шар OpenStreetMap Standard (`https://tile.openstreetmap.org/{z}/{x}/{y}.png` - тайли, картинки карти; атрибуція "© OpenStreetMap contributors"), Playwright Test як єдиний раннер тестів. Зміна stack потребує нового versioned decision record. Leaflet підключається тільки на клієнті.
- **Район:** Дуврська протока, прямокутник від 50.75° N, 0.95° E до 51.25° N, 1.95° E. Початковий вид: центр 51.00° N, 1.45° E, zoom 10.
- **Судно** - одна структура для демонстраційних і справжніх: `id` (рядок; для демонстрації `demo-1`…`demo-3`), `name` (рядок або `null`; порожній рядок → `null`), `lat`, `lon`, `speedKnots` (число або `null`), `courseDeg` (число в [0, 360) або `null`; курс руху, не напрямок носа), `timestamp` (ISO 8601 із зоною), `source` (`'demo'` | `'aisstream'`). Нуль і `null` - різні речі.
- **Картка:** ідентифікатор; назва як текст, не HTML; координати через `toFixed(5)` з хвостовими нулями (`51.00000, 1.45678`); швидкість з округленням до десятих без хвостових нулів і суфіксом (`12.3 kn`, `12 kn`, `0 kn`); курс `Math.round % 360` з градусом (`135°`); час повідомлення `12:00:00 UTC`; джерело ("Демонстраційні дані" / "AISStream"). Невідоме значення - "Немає даних". Кнопки закриття немає: картка закривається тільки вибором іншого судна; повторний клік і клік по карті вибір не змінюють. Порядок панелі згори вниз: кнопка (з'явиться пізніше), підпис джерела, картка.
- **Значок:** орієнтований за `courseDeg`; при `null` - нейтральний круглий. Атрибути `data-vessel-id="<id>"` і `data-icon="course"|"neutral"` - тести знаходять судна тільки за ними.
- **Демонстрація:** три судна "Демо-судно 1"…"Демо-судно 3"; у кожного 8-12 точок маршруту всередині району та швидкість руху у вузлах - літералами; тік `DEMO_TICK_MS = 2000`; курс - початковий азимут відрізка по великому колу (на старті - до другої точки, далі - від попередньої до поточної); час кроку - реальний час браузера, на старті - момент запуску таймера; тим самим тіком, яким судно приходить на останню точку, швидкість стає `0`, далі судно не змінюється; після оновлення сторінки - з початку. Пауза, перемотування, зациклення - немає. Перевірка імені `<b>Демо</b>` - тимчасовою правкою конфігурації, не комітиться.
- **Підпис джерела:** "Демонстраційні дані".
- **Запуск:** `http://localhost:3000`, тільки loopback.

### Завдання

**B-01. Каркас застосунку.** Next.js + React + TypeScript strict у порожній теці, запуск, Git з `.gitignore` для Node/Next, lock-файл. Критерій: `npm run dev` відкриває стартову сторінку; зайвих залежностей немає.

**B-02. Карта району.** Leaflet тільки на клієнті, шар OSM з атрибуцією, район і початковий вид з конфігурації, карта на всю доступну область. Критерій: пряме відкриття й оновлення сторінки працюють; зміна розміру вікна перемальовує карту без артефактів; `next build` проходить.

**B-03. Судно і значок.** Структура судна, одне демонстраційне судно всередині району, значок за курсом, нейтральний при `null`, підпис "Демонстраційні дані". Критерій: судно видно в районі, значок орієнтований.

**B-04. Вибір і картка.** Клік по судну відкриває картку за форматом вище; атрибути значка. Критерій: картка відповідає обраному `id`; повторний клік її не закриває; ім'я `<b>Демо</b>` відображається символами, не жирним.

**B-05. Три судна з маршрутами.** `demo-1`…`demo-3`, по 8-12 точок і швидкість кожного, літералами. Критерій: три судна в районі.

**B-06. Рух і зупинка.** Тік 2000 мс, курс - азимут відрізка, картка обраного судна оновлюється, зупинка на останній точці зі швидкістю `0` тим самим тіком; таймери не накопичуються при перемальовуваннях і очищаються при виході зі сторінки. Критерій: ручна перевірка - рух і зупинка видні; після hot reload у консолі один тік за інтервал, не два.

**B-07. Раннер і тести вибору.** Playwright Test з одним браузером, запуск dev-сервера з конфігурації; браузерні тести: на сторінці три елементи з `data-vessel-id`; клік по судну відкриває картку з його `id`; повторний клік її не закриває; запити до тайлів заблоковані. Критерій: тести зелені; інших тестових фреймворків немає.

### Результат тижня

**Після заняття 1:** B-01…B-04 - карта, одне судно без руху, картка; ручна перевірка виконана; checkpoint 01: запис, коміт, архів.

**Після заняття 2:** B-05…B-07 - три судна рухаються й зупиняються, картка оновлюється, тести вибору проходять; checkpoint 02: запис, коміт, архів.

Рух цього тижня перевіряється візуально; автоматична перевірка руху з керованим часом - завдання релізу R3, і в записі checkpoint це так і записується.

### Приклад очікуваної поведінки

Судно `demo-1` з маршрутом із 10 точок. Через 18 секунд після відкриття сторінки воно на останній точці; через 30 секунд - там само, у картці швидкість `0 kn`, курс і час останнього кроку. Картка `demo-1`, відкрита на 5-й секунді, до 18-ї секунди показує координати останньої точки.

## Частина B. Як робимо з Claude Code

Тут "ми" - той, хто веде агента: на занятті це ментор, при повторенні у своїй копії - ви.

### Метод тижня

Перший тиждень - чітко поставлене завдання з коротким повним циклом: `завдання → дослідження → рішення → зміна → перевірка → diff → наступний крок`. Кожне завдання backlog - один-два запити агенту. У кожному запиті три обов'язкові елементи:

- **межі** - що не чіпати і які функції не додавати (цього тижня: жодних заготовок під сервер, кнопку, справжні дані);
- **критерій перевірки** - як переконаємося, що готово;
- **посилання на завдання** - агент читає цей canonical root-level `SPRINT-01.md`, а не переказ.

### Порядок роботи

**До першого Edit.** Агент читає `PROJECT_BRIEF.md` і цей файл та пропонує план B-01…B-04 без правок. Перевіряємо план на зайве: create-next-app з прикладами, теки "на майбутнє", друга бібліотека карт. Тільки потім - реалізація.

**Каркас (B-01).** Один запит: мінімальний проєкт, Git, `.gitignore`, короткий `CLAUDE.md` зі стеком, командами запуску, межами тижня і правилом "секрети не читати й не виводити". У `CLAUDE.md` немає майбутніх вимог.

**Карта (B-02).** Пастка тижня: Leaflet звертається до `window` і ламає серверний рендеринг та збірку. Вимагаємо від агента клієнтське підключення і прогін `next build` як критерій. Друга пастка - не підключений CSS Leaflet або контейнер без висоти: карта сіра або роз'їжджається. Перевіряємо очима після кожної зміни.

**Судно і картка (B-03, B-04).** Структуру судна задаємо полями, а не описом - інакше агент вигадає свою. Формати картки - літералами з частини A. Перевірка "ім'я як текст" - руками: судно з ім'ям `<b>Демо</b>`.

**Рух (B-05, B-06).** Спочатку дані (маршрути літералами), потім рух. Вимагаємо один тік на всі судна, очищення таймера при виході зі сторінки й оновлення картки з того самого стану, що й карта. Перевірка накопичення таймерів: лічильник тіків у консолі після hot reload.

**Тести (B-07).** Встановлення браузера Playwright запускаємо у фоні - воно довге. Тести вибору не перевіряють рух - так і записується в checkpoint. Тайли блокуємо, інакше тест залежить від мережі. Судна шукаємо тільки за `data-vessel-id`.

**Review.** Після кожного завдання: "покажи diff, зістав із завданням, код не змінюй". Diff читаємо самі. Рішення фіксується явно: прийняти, повернути, зупинитися.

**Checkpoint.** Після рішення про приймання агент записує `docs/checkpoints/CHECKPOINT-0N.md` за шаблоном з репозиторію й робить коміт; архів цього коміту - крок публікації на занятті, при повторенні у своїй копії він не потрібен. У записі - тільки факти: як запустити, що зроблено, які команди виконані й з яким результатом, що перевірено візуально, що лишилося. У цьому репозиторії checkpoint-артефакти ще не створені; їхній шлях має бути погоджений окремим decision record.

### Приклади запитів

Формулювання - орієнтир, не скрипт.

- "Прочитай docs/tasks/PROJECT_BRIEF.md і docs/tasks/SPRINT-01.md. Запропонуй план завдань B-01…B-04 і критерії перевірки. Файли не редагуй, майбутні завдання не проєктуй."

- "Покажи diff з фокусом на таймерах і оновленні обраного судна. Відокрем перевірене тестом від перевіреного візуально. Код не змінюй."

### Що ви маєте зрозуміти до кінця тижня

- Чому Leaflet підключений тільки на клієнті і що сталося б інакше.
- Де живе стан суден і чому карта й картка читають з одного місця.
- Чому "Немає даних" і "0 kn" різняться з першої версії.
- Що доводять тести вибору і чого не доводять.

### Nice to have між заняттями

- Додати четверте демонстраційне судно з власним маршрутом.

## Частина C. Декомпозиція на bounded sessions

Ця частина фіксує план роботи, а не виконані результати. Позначені checks, evidence та acceptance стають фактичними лише після запуску відповідної сесії та запису результату в `EVIDENCE.md`.

### Стратегія handoff між сесіями

Одна сесія = один короткий bounded slice з окремим іменем. На початку наступної сесії читаються актуальні `SPRINT-01.md`, `TASK_SPEC.md`, останні записи `EVIDENCE.md` і `RUNBOOK.md`. Повний transcript чату не є необхідним.

Наприкінці сесії handoff має містити:

- фактично змінені файли;
- фактично виконані команди або manual checks та їхній статус;
- evidence ID і limitations;
- unresolved Unknowns і blockers;
- rollback/recovery path;
- наступну названу сесію та її bounded starting point.

План не є evidence: запланований check не можна називати пройденим до його фактичного запуску. Після кожного slice виконується human diff review і явно обирається `continue`, `revise` або `HOLD`.

### `R1-B01-SCAFFOLD` — каркас застосунку

- **B-01:** мінімальний Next.js + React + TypeScript strict проєкт, запуск, Git і lock-файл.
- **Goal:** отримати мінімальну локальну основу застосунку.
- **Non-goals:** Leaflet, карта, судна, AIS, серверна логіка та майбутні заготовки.
- **Check:** `npm run dev`; стартова сторінка; `.gitignore`; lock-файл; відсутність зайвих залежностей.
- **Evidence:** tree, manifest, lock-файл, фактичний output запуску та diff.
- **Acceptance:** застосунок запускається однією локальною командою й не містить непотрібного прикладного функціоналу.
- **Handoff:** передати наступній сесії фактичний запуск, список файлів і рішення щодо структури app directory; наступна — `R1-B02-MAP`.

### `R1-B02-MAP` — карта Дуврської протоки

- **B-02:** Leaflet лише на клієнті, OSM Standard з атрибуцією, район і початковий вид з конфігурації.
- **Goal:** показати стабільну карту на всю доступну область.
- **Non-goals:** судна, рух, картки, AIS і кнопка справжніх даних.
- **Check:** `next build`; пряме відкриття; refresh; resize; відсутність сірої карти або артефактів.
- **Evidence:** build output і manual checklist/screenshot з обмеженнями мережі.
- **Acceptance:** карта працює після прямого відкриття й оновлення, має атрибуцію та коректний initial view.
- **Handoff:** передати build/manual result і відомі map limitations; наступна — `R1-B03-VESSEL-MODEL`.

### `R1-B03-VESSEL-MODEL` — модель судна та значок

- **B-03:** узгоджена структура судна, одне demo-судно, значок за курсом або neutral при `null`.
- **Goal:** показати одне коректно описане демонстраційне судно на карті.
- **Non-goals:** рух, три маршрути, картка, AIS і таймери.
- **Check:** судно в межах району; `data-vessel-id`; `data-icon="course"|"neutral"`; підпис джерела.
- **Evidence:** code diff і manual check фактичних координат/значка.
- **Acceptance:** судно видно, значок відповідає `courseDeg` або `null`, джерело позначене як демонстраційне.
- **Handoff:** передати фактичну модель і перевірені атрибути; наступна — `R1-B04-VESSEL-CARD`.

### `R1-B04-VESSEL-CARD` — вибір і картка

- **B-04:** клік по судну відкриває картку у форматі узгоджених значень.
- **Goal:** показати картку саме обраного судна без HTML-інтерпретації назви.
- **Non-goals:** автоматичний рух, три судна, справжні дані та пошук.
- **Check:** `id`, name, coordinates, speed, course, timestamp, source; повторний клік; ім'я `<b>Демо</b>` як текст.
- **Evidence:** browser/manual check і screenshot або test output.
- **Acceptance:** картка відповідає `id`, невідомі значення — "Немає даних", `0 kn` не плутається з `null`.
- **Handoff:** передати формат картки й відомі UI limitations; наступна — `R1-B05-DEMO-ROUTES`.

### `R1-B05-DEMO-ROUTES` — три demo-судна

- **B-05:** `demo-1`…`demo-3`, по 8–12 точок маршруту та швидкість кожного.
- **Goal:** отримати три незалежні демонстраційні траєкторії всередині району.
- **Non-goals:** таймер, pause, rewind, loop, AIS і зміна конфігурації під час роботи.
- **Check:** три `data-vessel-id` на карті; усі точки маршрутів у районі; швидкості задані літералами.
- **Evidence:** конфігураційний diff і manual inspection координат.
- **Acceptance:** три судна видно одночасно з коректними іменами, маршрутами та початковими курсами.
- **Handoff:** передати перевірений набір demo data; наступна — `R1-B06-MOTION`.

### `R1-B06-MOTION` — рух і зупинка
